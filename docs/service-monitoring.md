# Sky 모니터링 준비

## 이번에 맡을 범위

우선 Sky 서비스 서버가 정상적으로 요청을 받고, 배포 작업 중에도 화면과 조회 API가 응답하는지 확인한다. 사용자 앱의 배포 성공 여부는 별도로 확인한다. Sky가 살아 있다고 게임까지 정상이라는 뜻은 아니다.

현재 확인한 코드는 `32c94e1b6d6633d8164786b009be2a783acde413` 기준이다. 아래 CloudWatch 구성은 준비안이며, 실제 계정에 알람이나 대시보드를 만든 상태는 아니다. 새 sky-infra가 올라오면 실제 ALB·ECS·EC2 이름과 로그 그룹을 연결한다.

이후 최신 플랫폼 `8969fd8`, 게임 `8b5f57b`를 확인해 기존 API용 수집기와 Prometheus·Grafana 설정을 추가했다. 실제 AWS 연결과 앱 단계별 지표는 아직 미완료다. [통합 모니터링 구성과 실행 방법](../ops/monitoring/README.md)에 현재 구현 범위를 정리했다.

## 먼저 볼 항목

| 구분 | 항목 | 확인하려는 것 | 수집 방법 |
| --- | --- | --- | --- |
| 서비스 접속 | 요청 수, 응답 시간 p95/p99, 실패율 | 부하가 늘 때 조회가 느려지거나 실패하는가 | k6 + ALB CloudWatch |
| ALB | 정상 타깃 수, 타깃 5xx, ALB 자체 5xx | 앱 장애와 라우팅 장애 구분 | AWS/ApplicationELB |
| ECS 서비스 | CPU·메모리, 실행/희망 태스크 수, 종료 이유, 배포 실패 | 자원 부족·OOM·태스크 재시작 확인 | ECS 지표와 서비스 이벤트; 태스크 수는 필요 시 Container Insights |
| EC2 호스트 | CPU, 메모리, 디스크 여유, 이미지 캐시 | 앱 Docker 빌드가 같은 호스트의 자원을 소모하는지 | EC2 지표 + 메모리/디스크용 CloudWatch Agent 추가 |
| 상태 저장 | 상태 디렉터리 쓰기 실패, 잠금 오류, 재시작 후 작업 기록 | 기존 배포 정보가 유지되는가 | 앱 로그 + 별도 재시작 검증 |
| 배포 작업 | 성공/실패 수, 전체 소요 시간, 단계별 실패 원인 | Sky가 실제로 배포를 완료하는가 | 작업 상태·이벤트 기록. 자동 집계/사용자 정의 지표는 후속 구현 |
| 배포된 게임 | HTTP 접속, WebSocket 연결·메시지 왕복, 승패 저장 | 외부에서 게임을 할 수 있는가 | 게임 전용 검증 및 기능 테스트 |

EC2 기본 지표에 호스트 메모리와 디스크 사용률은 없다. ECS 태스크 지표만 보면 호스트에서 실행되는 Docker 빌드의 사용량을 놓칠 수 있다. 실제 빌드 위치를 먼저 확인한다.

`/health`는 앱 프로세스가 HTTP에 응답하는지 확인하는 수준이다. AWS 배포 가능 여부, Docker 엔진, OpenAI 호출, 상태 저장 정상 여부까지 보장하지 않는다. `/api/jobs/{id}/health`는 외부 환경을 점검하고 기록도 변경하므로 k6 조회 부하에 넣지 않는다.

## 초기 알람 제안

처음에는 아래 기준으로 시작하고 정상 상태의 데이터를 본 뒤 조정한다. 확정된 운영 SLO는 아니다.

| 알람 | 초기 기준 | 확인/대응 |
| --- | --- | --- |
| 정상 타깃 없음 | HealthyHostCount Minimum < 1, 60초 단위 3개 중 2개 | 태스크 종료·헬스 체크 경로·배포 이벤트 |
| 서버 오류 증가 | 타깃 5xx 또는 ALB 5xx 각각 1분에 5건 이상, 3개 중 2개 | 앱 로그와 ALB 오류 원인 각각 확인 |
| CPU·메모리 지속 상승 | 각각 80% 이상 5분 지속 | 빌드 작업 여부, OOM, 요청 지연과 함께 판단 |
| 디스크 부족 | 호스트 여유 공간 20% 미만 | 캐시·이미지·작업 파일 점검. 자동 삭제는 별도 정책 필요 |
| 태스크 비정상 종료 | 종료 이벤트/OOM 발생 | 종료 이유·직전 버전·재배포 여부 확인 |

ALB 지표는 Sky 전용 로드 밸런서/타깃 그룹으로 한정한다. 요청이 없는 시간에는 일부 지표가 나오지 않으므로 누락 데이터를 정상으로 해석하지 않는다. 의도적인 서버 중지와 점검 시간도 기록한다. 알림은 SNS 생성뿐 아니라 수신 구독 확인과 테스트 알림까지 확인한다.

ALB TargetResponseTime과 k6의 HTTP 응답 시간은 측정 구간이 다르다. 둘을 같은 값으로 비교하지 않고 같은 시간대의 추세를 본다.

## 로그에서 남길 내용

- 실행 시각, 커밋/이미지 태그, 작업 ID, 단계, 결과, 소요 시간, 오류 종류.
- 오류가 난 요청과 ECS 태스크 종료 시각을 연결할 수 있는 정보.
- OpenAI 키, AWS 키, 세션 토큰, Cognito 쿠키, 업로드 코드 원문은 기록하지 않는다.

현재 코드의 작업 기록과 HTTP 로그를 먼저 사용한다. 배포 단계별 구조화 로그와 사용자 정의 CloudWatch 지표가 이미 있다고 가정하지 않는다. 이후 필요한 필드만 플랫폼 담당자와 맞춘다.

## 진행 순서

1. 실제 Sky 이미지가 올라오면 smoke로 nginx 임시 이미지와 구분한다.
2. 기준 부하에서 응답·자원·로그를 같은 시간대로 수집한다.
3. 단계적으로 부하를 올린 뒤 장시간 유지 테스트를 한다.
4. 승인된 배포 작업을 1개 진행하면서 조회 부하가 영향을 받는지 확인한다. 배포 자체를 k6로 반복 호출하지 않는다.
5. 실패·재배포·재시작 검증은 별도 일정으로 진행한다. 현재 구조의 중단 시간을 실제로 측정하고 무중단이라고 표현하지 않는다.

## 결과 정리

테스트 환경(태스크 CPU/메모리, EC2 종류, 태스크 수), 소스 SHA/이미지 태그, 시작·종료 시각, 작업 목록 크기, 부하 발생 위치, 프로필을 함께 남긴다. 결과는 요청 수, p95/p99, 오류율, dropped iterations, CPU/메모리/디스크 변화, 원인 및 개선 후 재측정으로 정리한다. 빈 작업 목록에서 나온 수치를 실제 작업이 쌓인 환경의 성능으로 일반화하지 않는다.
